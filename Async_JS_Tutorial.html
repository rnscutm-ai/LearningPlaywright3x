The Dispatch Board:
a field guide to async JavaScript

JavaScript runs on a single track, but it never waits idle — every async operation is a train that departs the main line, does its work off to the side, and gets dispatched back when it's done. This is the schedule.

Macrotasks setTimeout, I/O
This mirrors real execution order: synchronous code first, then the entire microtask queue drains, then one macrotask runs — repeat.

01

Callback

Foundational

The original way JavaScript handled "do this later": pass a function as an argument, and let whoever's holding it call it back when the work is done.

A callback is just a function handed to another function, to be invoked once some task — a timer, a network request, a file read — finishes. There's nothing magic about it; it's ordinary function-passing, used to defer execution.

basic-callback.js
function fetchUser(id, callback) {
  setTimeout(() => {
    const user = { id, name: "Priya" };
    callback(null, user); // (error, result) convention
  }, 1000);
}

fetchUser(42, (err, user) => {
  if (err) return console.error(err);
  console.log("Got user:", user.name);
});

Callbacks work fine for one async step. The trouble starts when steps depend on each other — you nest a callback inside a callback inside a callback, and the code staircases to the right. This is famously nicknamed "callback hell" or the "pyramid of doom":

callback-hell.js
getUser(id, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);
    getInvoice(orders[0].id, (err, invoice) => {
      if (err) return handleError(err);
      sendReceipt(invoice, (err) => {
        if (err) return handleError(err);
        console.log("Done — four levels deep.");
      });
    });
  });
});
Why this hurts Error handling is repeated at every level, the indentation obscures the actual logic, and reordering or parallelizing steps means restructuring the whole nest. Promises were designed specifically to flatten this shape.
  • Still everywhere: DOM events (addEventListener), Node's older APIs, and array methods like arr.forEach(callback) or arr.map(callback) all use callbacks — just not usually nested ones.
  • Error-first convention: Node-style callbacks pass (error, result) as the first two arguments, by convention, so the caller always checks err first.
02

new Promise

Core

A Promise is a ticket for a value that doesn't exist yet. It's issued immediately, and it settles — once — into either a delivered value or a reason it couldn't be delivered.

Every Promise exists in one of three states:

  • pending — the outcome hasn't happened yet.
  • fulfilled — the work succeeded; the promise now holds a value.
  • rejected — the work failed; the promise now holds a reason.

Once a promise settles (fulfilled or rejected), it's locked in permanently — it can never change state again or fire twice.

new-promise.js
const rollDice = new Promise((resolve, reject) => {
  // The "executor" runs immediately and synchronously.
  const value = Math.ceil(Math.random() * 6);
  setTimeout(() => {
    if (value >= 4) resolve(value);       // fulfilled
    else reject(new Error(`Rolled a ${value} — too low`)); // rejected
  }, 800);
});

rollDice
  .then(value => console.log("You rolled:", value))
  .catch(err => console.log("Failed:", err.message));

The new Promise((resolve, reject) => {...}) constructor is mainly for wrapping something that isn't already promise-based — a raw setTimeout, an old callback-style API, a websocket event. If you're calling a function that already returns a promise, you almost never need new Promise — just use or return that promise directly.

Common trap Wrapping a promise-returning function in another new Promise — the "Promise constructor antipattern." If doThing() already returns a promise, don't write new Promise((resolve, reject) => doThing().then(resolve).catch(reject)). Just return doThing();
  • Chaining: .then() returns a new promise, so calls can be chained: fetch(url).then(r => r.json()).then(data => ...).
  • Errors propagate: a single .catch() at the end of a chain catches a rejection from any step above it.
03

Async / Await

Core

Syntax sugar over Promises that lets asynchronous code read top-to-bottom, like synchronous code — without changing what's actually happening underneath.

Marking a function async does two things: it makes the function always return a Promise, and it unlocks the await keyword inside it. await pauses the function at that line until the awaited promise settles, then either returns its value or throws its rejection — letting you use plain try/catch for error handling instead of .catch() chains.

async-await.js
function delay(ms, value) {
  return new Promise(resolve => setTimeout(() => resolve(value), ms));
}

async function checkout(cartId) {
  try {
    const cart   = await delay(400, { id: cartId, total: 58 });
    const payment = await delay(600, { status: "approved" });
    console.log(`Cart ${cart.id} charged $${cart.total} — ${payment.status}`);
    return payment;
  } catch (err) {
    console.log("Checkout failed:", err.message);
    throw err;
  }
}

checkout("cart_9").then(() => console.log("Order pipeline finished."));

Compare this to the same logic written with raw .then() chains — same behavior, but async/await reads as a straight line instead of a chain of callbacks:

same-logic-with-then.js
function checkout(cartId) {
  return delay(400, { id: cartId, total: 58 })
    .then(cart =>
      delay(600, { status: "approved" }).then(payment => {
        console.log(`Cart ${cart.id} charged $${cart.total} — ${payment.status}`);
        return payment;
      })
    )
    .catch(err => {
      console.log("Checkout failed:", err.message);
      throw err;
    });
}
Common trap: accidental serialization Awaiting independent operations one after another makes them run in sequence even though nothing requires it — wasting time. If the operations don't depend on each other, start them together and await the group (see Promise.all, next). 
// Slow: 400ms + 600ms = ~1000ms total
const a = await delay(400, "a");
const b = await delay(600, "b");

// Fast: both run at once, ~600ms total
const [a2, b2] = await Promise.all([delay(400, "a"), delay(600, "b")]);
  • Top-level await: in ES modules, await can be used outside any async function, at the top of the file.
  • await only pauses that function: the rest of the program keeps running — it's not a global freeze, just a local one.
04

Promise.all

Combinator

Dispatch every train on the same signal, and wait for the whole convoy to arrive. If even one derails, the entire convoy is marked failed.

Promise.all(iterable) takes a collection of promises and returns a single promise that:

  • fulfills with an array of all results, in the same order as the input, once every promise has fulfilled;
  • rejects immediately with the reason from the first promise that rejects — the other promises keep running in the background, but their eventual results are discarded.
promise-all.js
function delay(ms, value) {
  return new Promise(resolve => setTimeout(() => resolve(value), ms));
}

async function loadDashboard() {
  const [profile, orders, notifications] = await Promise.all([
    delay(300, { name: "Priya" }),
    delay(500, { count: 12 }),
    delay(200, { unread: 3 }),
  ]);
  console.log(`${profile.name} · ${orders.count} orders · ${notifications.unread} unread`);
  // Total time ≈ 500ms (the slowest one) — not 300+500+200.
}

loadDashboard();
Fail-fast behavior One rejected promise rejects the whole batch, even if the other nine were about to succeed. If you need every result regardless of individual failures, use Promise.allSettled() instead — it never rejects, and resolves with a {status, value|reason} object per input.

When to reach for it: independent async operations that you need all of before continuing — loading several unrelated API endpoints for one page, resizing a batch of images, running the same validation against multiple records.

05

Promise.race

Combinator

Dispatch several trains toward the same platform. The instant the first one arrives — whether on time or derailed — the board updates. The rest are ignored.

Promise.race(iterable) settles as soon as the first input promise settles — with whatever outcome that one had, fulfilled or rejected. It doesn't wait for, or care about, the rest.

API call
900ms
Timeout
500ms
promise-race.js
function delay(ms, value) {
  return new Promise(resolve => setTimeout(() => resolve(value), ms));
}
function timeout(ms) {
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error("Timed out")), ms)
  );
}

async function fetchWithTimeout() {
  try {
    // Whichever settles first — the real call or the timeout — wins.
    const result = await Promise.race([
      delay(900, { data: "server payload" }), // the actual API call
      timeout(500),                            // a 500ms deadline
    ]);
    console.log("Success:", result);
  } catch (err) {
    console.log("Race lost:", err.message); // "Timed out" — 500 < 900
  }
}

fetchWithTimeout();
Signature use case: timeouts Promise.race's most common real job is racing a slow operation against a timer, so a hung request can't stall your app forever.
Note The "losing" promises are not cancelled — JavaScript has no built-in promise cancellation. They keep running to completion in the background; race just stops listening to them. For real cancellation, pair it with an AbortController.
06

Field Notes

Reference

How the pieces relate, and the other two combinators worth knowing about even though they didn't make the headline list.

ToolSettles whenBest for
Promise.all All fulfill, or the first one rejects You need every result; failure of one should abort the rest
Promise.race The very first promise to settle, win or lose Timeouts; taking whichever of several sources answers first
Promise.allSettled All promises have settled, regardless of outcome You want every result and every failure, none discarded
Promise.any The first promise to fulfill (ignores rejections until all fail) Try several sources; accept the first success, only fail if all fail

How async/await relates to Promises: they're not competitors. async/await is a syntax layer that sits directly on top of the Promise machinery — an async function always returns a Promise, and await is just a readable way to write .then(). Every combinator above still works the same when you await it:

bringing-it-together.js
async function loadEverything() {
  // 1. Wrap a legacy callback API in a Promise once, at the boundary.
  const legacyResult = new Promise(resolve =>
    oldCallbackApi((data) => resolve(data))
  );

  // 2. Run independent work in parallel, await the group.
  const [config, legacy] = await Promise.all([fetchConfig(), legacyResult]);

  // 3. Race a fetch against a hard deadline.
  const data = await Promise.race([fetchData(config), timeout(3000)]);

  return data;
}
Rule of thumb Callbacks → wrap in new Promise at the boundary, once. Sequential dependent steps → async/await. Independent steps you need all of → Promise.all. First-to-answer or a deadline → Promise.race. Need every outcome, success or fail → Promise.allSettled.
